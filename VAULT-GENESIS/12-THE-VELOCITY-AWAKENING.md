## The 10-Minute Rule: Velocity Gate

The 10-Minute Rule is the Phoenix system's primary velocity mechanism. It operates on two levels:

**Level 1: The Build Gate**
Every discrete task in the Phoenix build queue must produce a verifiable output within 10 minutes. If 10 minutes pass with no verifiable output, the task is flagged for audit. The audit determines: Is the task too large (needs decomposition)? Is the task blocked (needs escalation)? Is the task confused (needs clarification from Agent-100)?

The 10-minute window is not a hard deadline — it is a signal. A task that consistently fails the 10-minute output test is a task with a structural problem. Find the structural problem. Fix it. Do not accept chronic 10-minute failures as a normal build state.

**Level 2: The TMST Gate**
The TMST (10-Minute Shit Test) is the verification complement to the build gate. Once an output is produced, it gets 10 minutes of adversarial review. Two 10-minute windows per task: one for building, one for verifying. Twenty minutes total for a complete verified output cycle.

This is radically faster than the old model's review cycles — where outputs went through team review, manager approval, and stakeholder feedback before being accepted.

## Velocity Anti-Patterns

The following are velocity killers that Phoenix explicitly guards against:

**Anti-Pattern 1: Perfectionism Before Verification**
Building the perfect version of something before testing if the skeleton works. SKELETONONLY prevents this. Build the skeleton first. Perfect later.

**Anti-Pattern 2: Planning Beyond the Horizon**
Spending build time planning things that are 6 months away. PLANCONFIRMEXECUTE applies to the immediate next action. The 5-year vision is the horizon anchor, not the daily task list.

**Anti-Pattern 3: Explanation Overhead**
Pausing the build to explain to external parties what is being built. Explanation is a post-build activity. Build first, document in the Ledger, explain when the build is verified.

**Anti-Pattern 4: Premature Scale**
Optimizing for scale before the skeleton is verified. A system that scales wrong scales wrong faster. Verify the core first. Scale second.
