Simple sync design (KISS):

Object A (source) owns the chain — every append gets seq + prev-hash, then pushes the new head to Object B (mirror) before/after confirming.
B stores a byte-identical replica anchored on the same seq+hash, so it's verifiable (same hashes = no drift).
Reads can hit either. If A is unreachable, B accepts appends at the next free seq and A, when it's back, pulls and reconciles the missing range.
A head endpoint on each returns its current anchor — if A and B ever disagree, the ledger flags drift instead of silently splitting ("fail-closed").
That's the core. The one decision that shapes everything: do writes wait for both (strong sync — B must ack every append, so a dead B blocks new writes) or fire-and-forget (async sync — A always writes, B catches up later, you accept momentary divergence on failover)?
