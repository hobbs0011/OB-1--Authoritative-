## Overview

The Nonce Protocol governs cryptographic uniqueness enforcement across every Phoenix ledger event. A nonce is a value that is used exactly once. In the Phoenix system, a nonce is not optional metadata — it is a mandatory field on every ledger entry, every consensus vote, every Temporal Lock, every Phase Anchor, and every signed agent communication. A ledger event without a valid nonce is not a ledger event. It is rejected at the write boundary before it touches the SQLite schema.

The nonce's function is replay-attack prevention. A replay attack is an attempt to re-execute a valid past transaction — one that was legitimate when first executed — in a new context where its execution would cause unintended effects. Without nonces, an attacker who captures a valid signed ledger entry can re-submit it and the system, lacking a mechanism to distinguish the first submission from the second, may execute it again. With nonces, the re-submission fails at the nonce registry check: the nonce has already been consumed, and a consumed nonce cannot be valid again.

Replay attacks are not theoretical in append-only distributed ledger systems. They are a documented attack class. The Nonce Protocol is the Phoenix system's complete defense against this class. It is not one layer of defense among several — it is the layer. Every other integrity mechanism (Merkle chain, Temporal Locks, signature verification) is necessary but not sufficient to prevent replay attacks without the Nonce Protocol.

## Nonce Generation Algorithm

Nonces in the Phoenix system are deterministic-in-inputs but unpredictable-without-inputs. They are not random numbers. A purely random nonce cannot be independently re-derived for verification purposes. A deterministic nonce derived from event-specific inputs can be verified by any party that has the inputs, without access to the nonce registry.

The generation algorithm:

```
INPUTS:
  event_id        — UUID v4 of the event being nonce-protected
  author_id       — identity hash of the agent or process generating the event
  timestamp_ns    — nanosecond-precision atomic clock value from the DO time source
  system_entropy  — 32-byte entropy value from the current epoch's entropy pool

COMPUTATION:
  nonce_preimage = CONCAT(event_id, "||", author_id, "||", timestamp_ns, "||", system_entropy)
  nonce = SHA256(nonce_preimage)

OUTPUT:
  64-character hex string (256-bit nonce)
```

The `system_entropy` value is the critical unpredictability input. It is generated by the `PhoenixEntropyDO` once per epoch (epoch length: 60 seconds) and distributed to all active Durable Objects at epoch boundary. The entropy value is itself stored in the nonce registry — an entropy value is never reused across epochs. With a new entropy value every 60 seconds, two events that share the same `event_id`, `author_id`, and `timestamp_ns` (which should be impossible, but is the adversarial case) cannot produce the same nonce unless they also share the same entropy value, which requires predicting or stealing the epoch entropy.

The 64-character hex nonce output is stored in the `nonces` table in the `PhoenixLedgerDO` SQLite schema and in the `nonce_ref` field of the ledger entry it protects.

## Nonce Registry in SQLite

```sql
CREATE TABLE nonces (
    nonce_id        TEXT PRIMARY KEY,            -- UUID v4 (internal registry record ID)
    nonce_value     TEXT NOT NULL UNIQUE,        -- 64-char hex SHA256 nonce
    event_id        TEXT NOT NULL,               -- event this nonce protects
    author_id       TEXT NOT NULL,               -- generating agent/process
    epoch_id        TEXT NOT NULL,               -- entropy epoch at generation time
    generated_at    INTEGER NOT NULL,            -- Unix epoch milliseconds
    consumed_at     INTEGER NOT NULL,            -- same as generated_at for first consumption
    expires_at      INTEGER NOT NULL,            -- see Nonce Expiry section
    status          TEXT NOT NULL DEFAULT 'CONSUMED',  -- CONSUMED | EXPIRED | COLLISION_FLAGGED
    collision_ref   TEXT                         -- NULL unless COLLISION_FLAGGED
);

CREATE UNIQUE INDEX idx_nonces_value ON nonces(nonce_value);
CREATE INDEX idx_nonces_event ON nonces(event_id);
CREATE INDEX idx_nonces_expires ON nonces(expires_at);
CREATE INDEX idx_nonces_status ON nonces(status);
```

Every nonce, the moment it is generated, is written to the registry with status CONSUMED. There is no "PENDING" state. Nonce generation and consumption are a single atomic operation. The nonce does not exist in the registry in an unconsumed state — if the event creation fails after nonce generation, the nonce is still consumed. The failed event's nonce is permanently retired. Nonces are not recycled from failed events.

The UNIQUE constraint on `nonce_value` is the primary enforcement mechanism. An attempt to insert a nonce that already exists in the registry fails at the database level before any application code can act on it. This is defense in depth: the application layer checks the registry before generating (to verify entropy is functioning), the database layer rejects duplicates regardless.

## Replay-Attack Prevention

The replay-attack prevention sequence executes at the ledger write boundary:

```
STEP 1: Event submitted to ledger write endpoint
STEP 2: Extract nonce_ref from event payload
STEP 3: Query nonces table: SELECT status FROM nonces WHERE nonce_value = ?
  → Result: row not found  → REJECT: "NONCE_UNKNOWN"
  → Result: EXPIRED        → REJECT: "NONCE_EXPIRED"
  → Result: COLLISION_FLAGGED → REJECT: "NONCE_COLLISION" + alert AGENT-100
  → Result: CONSUMED       → PROCEED to Step 4
STEP 4: Verify nonce derivation: recompute SHA256(event_id || author_id || timestamp_ns || epoch_entropy)
  → Mismatch → REJECT: "NONCE_INVALID" (nonce does not match event fields)
  → Match    → PROCEED to Step 5
STEP 5: Verify timestamp freshness: timestamp_ns must be within [now - 30s, now + 5s]
  → Outside window → REJECT: "NONCE_TIMESTAMP_STALE" (replay of old event)
  → Within window  → PROCEED to write
STEP 6: Write ledger entry with nonce_ref, write to entries table
STEP 7: Log successful consumption in nonces.consumed_at (already set at generation)
```

The 30-second backward window in Step 5 accounts for network latency and DO scheduling jitter. The 5-second forward window accounts for clock skew between DOs. Events older than 30 seconds are rejected as potentially replayed, regardless of nonce validity. An attacker who captures a valid signed event must replay it within 30 seconds — a window short enough to make replay operationally difficult and detectable via concurrent event monitoring.

## Nonce Expiry and Garbage Collection

Nonces do not live in the registry forever. The registry would grow without bound if they did. Nonces expire according to the following schedule:

| Event Class | Nonce Retention Period |
|-------------|----------------------|
| Standard ledger entry | 7 days |
| Consensus vote | 30 days |
| Temporal Lock | Permanent (never expires) |
| Phase Anchor | Permanent (never expires) |
| Agent communication | 24 hours |
| Heartbeat challenge | 1 hour |
| Simulation event | 24 hours |

Permanent nonces (Temporal Lock, Phase Anchor) are never garbage collected. They are the cryptographic anchors of the ledger history. Their registry entries are the proof that the nonces were legitimately generated at the claimed times. Deleting them would be equivalent to destroying evidence.

Expiry garbage collection runs as a scheduled Durable Object alarm every 6 hours:

```typescript
async function nonceGarbageCollect(storage: DurableObjectStorage): Promise<void> {
  const now = Date.now();
  const result = await storage.sql.exec(
    `UPDATE nonces SET status = 'EXPIRED' WHERE expires_at < ? AND status = 'CONSUMED'`,
    now
  );
  // Mark expired; do not DELETE. Expired records stay in registry for audit trail.
  // Physical deletion only after 90-day archive window.
  const archived = await archiveExpiredNonces(storage, now - (90 * 24 * 60 * 60 * 1000));
  await logGCRun(storage, { expired_marked: result.rowsWritten, archived });
}
```

Expired nonces are not immediately deleted — they are marked EXPIRED and retained for 90 days in the live registry, then archived to R2 cold storage before deletion from the hot SQLite schema. The 90-day retention ensures that any delayed forensic audit can access nonce records for events that occurred within the past quarter. R2 archive retention is indefinite.

## Cross-Region Nonce Synchronization via Durable Objects

The nonce registry in a single `PhoenixLedgerDO` is authoritative for events written to that DO instance. Because Cloudflare Durable Objects provide strong consistency within a single instance, nonce uniqueness is guaranteed within an instance by the UNIQUE constraint. The cross-region challenge arises when multiple DO instances operate concurrently — as they do in the Phoenix multi-region deployment — and an attacker attempts to replay an event from Region A at Region B before cross-region synchronization occurs.

Cross-region nonce synchronization protocol:

**Nonce broadcast**: When a nonce is consumed in any regional DO instance, the nonce value is broadcast to all peer DO instances via the `PhoenixNonceSyncDO` — a dedicated synchronization DO that maintains nonce cross-references across regions.

**Sync latency SLA**: Cross-region nonce broadcast must complete within 2 seconds of the original consumption. The 30-second replay window in the write boundary check creates a natural buffer: a replayed event arriving at a different region within 30 seconds of the original will be rejected if the sync has propagated (within 2 seconds), or will be caught by the timestamp staleness check after 30 seconds.

**Sync failure handling**: If the cross-region broadcast fails (the `PhoenixNonceSyncDO` is unreachable), the consuming DO logs a SYNC_FAILURE event and enters CAUTIOUS mode: all incoming events from other regions are held in a 30-second verification queue rather than being accepted immediately. The queue allows the sync channel to recover before events are processed. Events that cannot be verified within 60 seconds of arrival are rejected and must be resubmitted.

**Idempotent sync**: Nonce broadcast messages are themselves nonce-protected to prevent the sync protocol from being the attack vector. A `PhoenixNonceSyncDO` that receives a duplicate sync message (same nonce value) silently discards it — it already has the record.

## Catastrophic Nonce Collision Response Procedure

A nonce collision is the condition where two distinct legitimate events share the same nonce value. This should be computationally impossible — the SHA256 nonce generation algorithm has a collision probability of approximately 2^(-128) for any two inputs. However, the system is designed to handle it as a catastrophic event, not as a theoretical impossibility.

A nonce collision is detected when:
1. A nonce generation produces a value that already exists in the registry as CONSUMED (not EXPIRED), and
2. The existing consumed nonce belongs to a different event_id than the one being generated.

Detection triggers the CATASTROPHIC_NONCE_COLLISION response:

```
T+0:   SYSTEM HALT — all ledger writes suspended across all regional instances
T+0:   COLLISION_FLAGGED status set on both affected nonce records
T+0:   Severity 5 drift event generated: type NONCE_COLLISION
T+0:   AGENT-100 emergency notification dispatched
T+1m:  Forensic Audit initiated: NONCE_COLLISION classification
T+1m:  PhoenixEntropyDO halted — no new entropy distributed until root cause identified
T+5m:  AGENT-100 response deadline (Level 4 escalation if no response)

INVESTIGATION PATH:
  Phase 1: Verify the collision is genuine (not a software bug in the detection logic)
  Phase 2: Audit the entropy pool — entropy reuse is the most likely cause
  Phase 3: Audit the timestamp source — clock regression can cause input collision
  Phase 4: If genuine: document as a cryptographic event, escalate to full architectural review
  Phase 5: Rotate entropy source, regenerate entropy pool, re-verify all recent nonces
  Phase 6: Resume with enhanced monitoring — every nonce generation logged at DEBUG level
             for 72 hours following the collision event

RESUME CRITERIA:
  All of the following must be satisfied before ledger writes resume:
  □ Root cause identified and documented
  □ Collision mechanism cannot recur with current entropy source
  □ Last 10,000 nonces re-verified for uniqueness
  □ AGENT-100 explicit authorization to resume
  □ Forensic Audit report finalized
```

A genuine SHA256 nonce collision, caused by the hash function rather than by entropy or timestamp inputs, would indicate a cryptographic breakthrough with implications far beyond the Phoenix system. In that scenario, the Nonce Protocol is paused pending architectural replacement. The system halts rather than operates with a broken cryptographic primitive. Operating with broken cryptography is not acceptable at any stage of the Phoenix deployment.
