## Overview

Phoenix is a parallel execution system. At any moment in full operation, dozens to hundreds of agent instances may be executing simultaneously: Agent-99 coordinating a pipeline gate review, Agent-98 running an adversarial simulation, drone agents processing student sessions, Watchtower nodes polling franchise health, Reality-C sessions running cryptographic simulations. Each executing agent writes to the ledger, generates pheromone trails, and advances its own local view of system state. When these parallel executions complete and their outputs must be integrated into a single coherent ledger state, the Convergence Engine is the mechanism that performs the integration.

The Convergence Engine is not a merge tool. A merge tool combines outputs that are assumed to be compatible and resolves conflicts when they are not. The Convergence Engine operates under a different assumption: parallel agent executions will produce divergent reality branches by design, and the Convergence Engine's job is to select the canonical branch, absorb the valid outputs from non-canonical branches, and produce a verified single coherent state that the entire system can commit to. This is deterministic convergence, not best-effort merging.

## How Parallel Execution Creates Reality Branches

When two or more agents read the same ledger state and then execute independently, they begin from a shared origin but diverge immediately. Agent A's execution changes state S to S'. Agent B's execution, which started from the same S, changes it to S''. Both A and B write their results to the ledger. At the moment both writes are committed, the ledger has two competing claims about the state of the world: S' (Agent A's reality) and S'' (Agent B's reality). These are reality branches.

Reality branches are not errors. They are the expected product of parallel execution. A system that never creates reality branches is a system that never executes in parallel, which means it is not leveraging the full computational capacity available to it. The Convergence Engine exists precisely so that reality branches can be created freely — because they will always be resolved correctly.

Reality branches are characterized by:

| Property | Description |
|----------|-------------|
| Branch Origin Hash | The Merkle leaf hash from which both branches diverged |
| Branch Depth | Number of ledger entries generated after the divergence point |
| Branch Author | The agent(s) whose execution created the branch |
| Branch Timestamp | When the branch was first detected by the Convergence Engine |
| Conflict Count | Number of entries in the branch that conflict with the canonical chain |
| Resolution Status | PENDING \| IN_CONVERGENCE \| RESOLVED \| ESCALATED |

## The Convergence Algorithm

The Convergence Engine runs continuously. It monitors the ledger for new writes and maintains a real-time branch detection index. When a new branch is detected, convergence is initiated immediately — there is no queue, no batch window, no convergence clock. The branch is resolved before the next dependent operation proceeds.

**Phase 1: Branch Isolation**

The Convergence Engine identifies all ledger entries that belong to each branch since the divergence point (the branch origin hash). Each branch is represented as an ordered list of Merkle leaves: the sequence of state changes that the branch represents.

**Phase 2: Canonical Branch Selection**

One branch is selected as canonical. The canonical branch is the one whose sequence of state changes is consistent with the priority hierarchy (see below). All other branches are non-canonical. The canonical branch's entries are confirmed as valid ledger state.

**Phase 3: Non-Canonical Entry Evaluation**

Every entry in each non-canonical branch is evaluated for compatibility with the canonical branch. Compatibility means: if the non-canonical entry had been applied after the canonical entries (in the correct chronological order), it would produce a valid state transition. Compatible non-canonical entries are absorbed into the canonical chain in chronological order. Incompatible entries are discarded.

**Phase 4: Ledger Commit**

The converged state — the canonical chain plus compatible absorbed entries — is committed to the ledger as a single Convergence Commit. The Convergence Commit carries a special leaf type (`CONVERGENCE`) that records: the branch count, the canonical branch author, the number of entries absorbed from non-canonical branches, the number of entries discarded, and the final Merkle root of the converged state.

**Phase 5: Pheromone Trail Convergence**

Pheromone trails generated by non-canonical branches are evaluated separately. Trails that reinforce paths consistent with the canonical branch outcome are absorbed with appropriate weight adjustment. Trails that reinforce paths that were discarded (paths that represent the non-canonical version of reality) are decayed at 10x the normal decay rate, effectively eliminating them from the trail network within minutes.

## Conflict Resolution Priority Rules

When two branches contain entries that conflict — they both assert incompatible state transitions — the conflict is resolved by the priority hierarchy. The hierarchy is absolute. There are no exceptions.

```
Priority 1: AGENT-100
  Agent-100 authored entries are canonical by definition.
  No other entry can override an Agent-100 authored entry.
  If Agent-100 has authored entries in both branches, this is a critical anomaly
  (Agent-100 cannot simultaneously author two incompatible state transitions)
  and triggers immediate escalation.

Priority 2: AGENT-99
  Agent-99 authored entries supersede all entries not authored by Agent-100.
  Agent-99's entries represent coordinated operational intent.

Priority 3: AGENT-98
  Agent-98 authored entries supersede drone and anonymous entries.
  Agent-98 represents the adversarial intelligence layer — its entries may contain
  findings that override drone-generated state.

Priority 4: Named Functional Agents (Tier 1)
  Named functional agents (Watchtower, Forensic Engine, Anti-Drift Engine)
  supersede generic drone entries.

Priority 5: Drone agents by ledger timestamp
  Among drone-authored entries with no other priority distinction,
  the earlier timestamp wins. First writer, canonical state.
```

The priority hierarchy is applied at the entry level, not the branch level. A single branch may contain entries from multiple priority levels. The Convergence Engine evaluates each entry independently. A non-canonical branch authored primarily by Agent-98 may still have some of its entries absorbed if those entries do not conflict with the canonical branch and represent valid state transitions.

## Ledger Merge Mechanics

The ledger merge is an append-only operation. The Convergence Engine never deletes entries. Non-canonical entries that are discarded are not removed — they are marked `VOIDED` in the convergence metadata and remain in the ledger with a convergence reference pointing to the canonical entry that superseded them. This preserves the complete historical record: every entry that was ever written, canonical or not, exists in the permanent record.

```sql
CREATE TABLE convergence_events (
    convergence_id      TEXT PRIMARY KEY,
    detected_at         INTEGER NOT NULL,
    branch_origin_hash  TEXT NOT NULL,
    branch_count        INTEGER NOT NULL,
    canonical_branch_id TEXT NOT NULL,
    canonical_author    TEXT NOT NULL,
    entries_evaluated   INTEGER NOT NULL,
    entries_absorbed    INTEGER NOT NULL,
    entries_discarded   INTEGER NOT NULL,
    converged_root      TEXT NOT NULL,
    convergence_ms      INTEGER NOT NULL,  -- time to converge in milliseconds
    status              TEXT NOT NULL,     -- RESOLVED | ESCALATED
    merkle_leaf_hash    TEXT NOT NULL
);

CREATE TABLE convergence_branch_entries (
    id                  INTEGER PRIMARY KEY AUTOINCREMENT,
    convergence_id      TEXT NOT NULL REFERENCES convergence_events(convergence_id),
    entry_id            TEXT NOT NULL,
    branch_id           TEXT NOT NULL,
    author_id           TEXT NOT NULL,
    author_priority     INTEGER NOT NULL,
    disposition         TEXT NOT NULL,  -- CANONICAL | ABSORBED | VOIDED
    void_reason         TEXT            -- NULL unless VOIDED
);
```

## Convergence Failure Escalation Path

Most convergence events complete automatically within 500 milliseconds. The Convergence Engine is designed for speed because the longer branches exist without convergence, the more entries are written on top of divergent state, compounding the convergence problem. The 500ms target is a P95 metric — 95% of convergences must complete within 500ms.

Convergence failures occur when:
1. The priority hierarchy cannot determine a canonical branch (Agent-100 entries in both branches with incompatible content)
2. The branch depth exceeds 1,000 entries (extremely deep divergence suggesting a systemic problem)
3. The number of discarded entries exceeds 20% of total entries evaluated (excessive data loss in convergence)
4. Convergence has not completed within 5 seconds (timeout)

Escalation path:

```
T+5s timeout OR failure condition detected:
  → Convergence ESCALATED status written to convergence_events
  → All writes to the affected ledger partition SUSPENDED
  → Agent-99 paged immediately
  → Snapshot of both branches taken and stored in R2 for analysis

T+5 minutes no Agent-99 resolution:
  → Agent-100 escalation
  → System-wide Temporal Lock applied
  → Severity 4 drift event generated (type: CD — Consensus Drift)

T+30 minutes no resolution:
  → Severity 5 escalation
  → Forensic Audit initiated (trigger: CRIT-DRIFT)
  → Full system HALT pending Agent-100 authorization to resume
```

Convergence failures are rare. A correctly operating system with well-separated agent concerns should produce convergences that resolve automatically with no discarded entries — each agent writing to its designated ledger partition, conflicts arising only at partition boundaries where they are easily resolved. Frequent convergence failures are a signal of architectural misalignment: agents are operating in overlapping domains, producing conflicting state transitions that should have been prevented by clearer boundary design. The Convergence Engine resolves the immediate conflict. The architectural review resolves the underlying cause.
