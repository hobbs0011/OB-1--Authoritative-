# PCC-3 Research Report: Autonomous Agent Loop Patterns for Fixed Time Windows

## WHAT WAS ASKED

Best practices for running an AI agent autonomously for 1 hour that: drains a backlog queue, logs discoveries, self-reports metrics, and competes against sibling agents.

## PATTERN 1 — The Planner-Worker-Judge Triad (Most Proven)

**Source:** [nibzard/awesome-agentic-patterns](https://github.com/nibzard/awesome-agentic-patterns/blob/main/patterns/planner-worker-separation-for-long-running-agents.md)

The single most battle-tested pattern for long-running autonomous work. Three roles:

- **Planner** — explores the queue/codebase, spawns sub-planners, creates tasks. Planning itself is parallelized and recursive.
- **Worker** — operates in isolation, no cross-worker coordination. Executes only its assigned task.
- **Judge** — evaluates whether objective is met or iteration should continue.

**Key mechanic:** "Fresh starts" at each cycle. Workers get a new context window per task to prevent drift and tunnel vision. This is the anti-pattern to long-context degradation.

**Proven scale:** Hundreds of concurrent workers running for weeks on large codebases.

**Failure modes (documented):**
- Over-coordination: an "integrator" quality-control role created more bottlenecks than it solved — eliminated in production.
- Early termination: models "tend to stop early and take shortcuts" — Judge layer is the mitigation.
- Context drift: agents lose goal fidelity over long runs without fresh-start cycles.

## PATTERN 2 — LangGraph StateGraph with Hard Budget Caps

**Source:** [MatterAI self-correcting loops guide](https://www.matterai.so/guides/agentic-workflows-building-self-correcting-loops-with-langgraph-and-crewai-state-machines), [LangGraph timeout docs](https://langchain-cn.readthedocs.io/en/latest/modules/agents/agent_executors/examples/max_time_limit.html)

LangGraph implements time-bounded execution via `should_continue()` gates on conditional edges. The `AgentState` TypedDict tracks:

- `iterations` — retry count hard cap (5–15 iterations recommended)
- `total_tokens` — cumulative spend (50k token ceiling common)
- `quality_score` — normalized LLM-as-judge score (0–1)
- `errors` — classified failure modes (syntax / logic / timeout / API)

**For a 1-hour time window:** LangGraph does NOT enforce wall-clock deadlines natively. You inject `start_time = time.time()` into the state at initialization, and `should_continue()` checks `time.time() - start_time &lt; 3600`. No built-in scheduler. Entirely custom.

**Durable execution (LangGraph v1.0+):** Compile graph with PostgreSQL checkpointer — `StateSnapshot` saved at every super-step keyed by `thread_id`. If the runner dies mid-session, `resume_from_checkpoint(thread_id)` picks up exactly where it stopped. Validated in production.

**Failure modes:**
- No clock enforcement without custom implementation — easy to miss.
- Checkpointer adds latency per step — 50–200ms per DB write at scale.
- `max_iterations=15` without wall-clock guard allows runaway if LLM calls are fast.

## PATTERN 3 — Cloudflare Durable Objects: Hibernate-Wake Architecture

**Source:** [CF Long-Running Agents docs](https://developers.cloudflare.com/agents/concepts/long-running-agents/), [CF Worker limits](https://developers.cloudflare.com/workers/platform/limits/)

**Critical constraint:** CF Workers/Queues/Crons are all hard-capped at **15 minutes** per invocation. A 1-hour loop cannot run in a single Worker invocation.

**The correct CF pattern for 1 hour:**

A **Durable Object** is the only CF primitive that supports true persistence with no compute cost when idle. The architecture:

1. DO wakes via HTTP trigger or `schedule()` alarm.
2. Drains one batch from queue (e.g., 5–10 items), persisting progress to SQLite after each item.
3. Schedules next alarm for N seconds out (e.g., `scheduleEvery(30, "processNextBatch")`).
4. Hibernates — zero cost until alarm fires.
5. Repeats across the full 1-hour window via chained alarms.

**For operations exceeding ~70–140 seconds:** Wrap in `keepAliveWhile()` to reset the inactivity eviction timer.

**For metric reporting:** Persist a structured state object (step count, discoveries, errors, last-run timestamp) to SQLite — this doubles as recovery context and as the self-report payload.

**Failure modes:**
- In-memory variables do not survive hibernation — only `setState()` and `this.sql` persist. Forgetting this = silent state loss.
- `keepAlive` works for minutes, not hours — use Workflows or callback patterns for single operations &gt;15 min.
- Alarm at-least-once delivery: DO alarms can fire more than once under failure — operations must be idempotent.

## PATTERN 4 — Event-Driven Four-Pattern Matrix (Confluent)

**Source:** [Confluent event-driven multi-agent systems](https://www.confluent.io/blog/event-driven-multi-agent-systems/)

Four proven patterns for multi-agent coordination, each with a specific use case:

| Pattern | Mechanism | Best For |
|---|---|---|
| **Orchestrator-Worker** | Central topic dispatch, consumer group balancing | Queue drain with load balancing |
| **Hierarchical** | Recursive tree, each node is orchestrator for its subtree | Sibling competition inside a parent |
| **Blackboard** | Shared topic as knowledge base, no direct agent comms | Async discovery logging |
| **Market-Based** | Bid/ask topics, market-maker matching | Competing sibling agents — directly applicable |

**For sibling competition:** The Market-Based pattern is the academic match. Agents post bids (discoveries/scores) to a bid topic; a market maker publishes rankings to an ask/result topic. No direct agent-to-agent coupling. Failure of one sibling does not block others.

## PATTERN 5 — MultiAgentBench KPI Framework (Academic Baseline)

**Source:** [MultiAgentBench arxiv 2503.01935](https://arxiv.org/html/2503.01935v1)

The only peer-reviewed benchmark specifically for competitive multi-agent evaluation.

**Metric collection approach:**
- KPI = individual milestone contributions (nⱼ) / total milestones (M) — normalized 0–1.
- An LLM-based detector continuously monitors the iterative process to identify which milestones have been achieved (not a human reviewer, not a regex — a judge LLM).
- Communication Score (5-point scale), Planning Score (strategy adaptation), and Overall Coordination Score are averaged.

**Time/iteration management:**
- Max iterations vary by task (5 for research tasks, 20 for Minecraft).
- Ablation result: **performance degrades beyond 7 iterations** — "excessive iterations may lead to coordination degradation due to communication overhead."
- Communication iteration limits are separately configured (default: 5).

**Key finding for your use case:** More iterations ≠ better outcomes. There is an empirical degradation curve. For a 1-hour window, this implies bounded batch sizes with inter-batch pauses are better than a single continuous loop.

## PATTERN 6 — Temporal Workflow: Heartbeat-Based Deadline Enforcement

**Source:** [Temporal queue draining post](https://martinuke0.github.io/posts/2026-03-24-orchestrating-distributed-task-queues-with-temporal-and-python-for-resilient-agentic-microservices/)

Temporal is the most mature queue-drain-with-deadline framework. Key mechanics:

- `start_to_close_timeout` on every activity — hard cap per operation (30s for payments, 10s for reservations in production examples).
- **Heartbeat monitoring** for extended tasks: activities ping the Temporal server at intervals; if no heartbeat arrives within the window, the activity is assumed dead and retried.
- Fan-out parallelism via child workflows for elastic backlog drain.
- Monitored signals: `temporal_task_queue_pending_tasks` (backlog depth), `temporal_activity_failure_total`, `temporal_workflow_execution_latency`.
- Alert threshold seen in production: `&gt;1000 tasks pending`.

**Thundering herd mitigation:** Randomized backoff on retry storms — critical when a queue unfreezes after a blockage and all agents attempt simultaneous catch-up.

## SYNTHESIZED BEST PRACTICE FOR YOUR EXACT USE CASE

**Profile:** 1-hour window, queue drain, discovery logging, self-report metrics, sibling competition.

**Recommended architecture (composite of all above patterns):**

### Execution model
Use **Durable Objects + chained alarms** on CF, or **Temporal workflows** off-CF. Do NOT use a single long-running Worker/cron — both hit the 15-minute wall.

### Loop structure
```
init: { start_time, budget_seconds=3600, items_processed=0, discoveries=[], errors=[] }

on_each_alarm_wake:
  1. Check: (now - start_time) &lt; budget_seconds → if no, write final report, stop
  2. Pop N items from queue (N = 5–10 to stay under 15-min alarm window)
  3. Process each item → classify result → append to discoveries[] if relevant
  4. Persist state to SQLite / KV (idempotent write)
  5. Schedule next alarm in 30–60 seconds
  6. Write partial metrics to shared Blackboard topic / KV key
```

### Sibling competition
Use the **Blackboard or Market-Based pattern**: each sibling writes its `{ agent_id, items_processed, discoveries_count, score }` to a shared KV key or topic on every alarm cycle. A lightweight scorer reads all entries and publishes a leaderboard. No direct sibling-to-sibling communication — decoupled by design.

### Metric self-report
Persist a structured object on every write cycle (not just at end):
```json
{ "agent_id": "...", "run_start": 1234567890, "elapsed_s": 1820,
  "items_processed": 47, "discoveries": [...], "errors": 3,
  "last_checkpoint": "...", "score": 0.74 }
```
This is simultaneously the recovery checkpoint and the metrics payload — same write, dual purpose (CF Agents docs pattern).

### Failure mode defenses
| Risk | Mitigation |
|---|---|
| Silent state loss on eviction | Only write to `setState()` / SQLite, never in-memory |
| Idempotency on alarm re-fire | Include `item_id` check before processing — skip if already in discoveries[] |
| Context drift | Fresh context window per batch (Planner-Worker pattern) — do NOT carry full history across 60 iterations |
| Coordination overhead | Cap inter-agent communication (MultiAgentBench finding: degrade &gt;7 coordination rounds) |
| Queue exhaustion before deadline | Track `queue_depth` at each cycle; if 0, switch to discovery-consolidation mode rather than idling |
| Thundering herd on restart | Randomized jitter on first alarm (Temporal pattern) |

## FAILURE MODES SUMMARY (PROVEN IN PRODUCTION)

1. **Early termination** — models shortcut before window closes. Mitigation: Judge layer that explicitly checks "has time budget expired?" not just "is task done?"
2. **Over-coordination** — quality-control integrator role becomes bottleneck. Mitigation: remove it; let Judge be the only evaluator.
3. **Context drift** — long runs degrade goal fidelity. Mitigation: fresh context windows per batch.
4. **In-memory state loss** — hibernation evicts non-persisted variables silently. Mitigation: SQLite-only state.
5. **Coordination degradation** — multi-agent systems degrade beyond 7 coordination rounds (empirical). Mitigation: limit leaderboard sync frequency, not per-item.
6. **Thundering herd** — all agents retry simultaneously after blockage. Mitigation: randomized jitter.
7. **Duplicate processing** — alarm at-least-once delivery fires twice. Mitigation: idempotency check on item_id before every operation.

## Key Concepts for Long-Running Agents

A long-running agent is not a process that runs continuously—it is an entity that exists continuously but runs intermittently. This is a fundamental distinction when building autonomous agents on Cloudflare.

## The Pattern for Long-Running Work

When an agent frequently kicks off work that takes far longer than any single activation (like a CI pipeline running 20 minutes or a video asset taking hours to generate), the agent should not stay alive for any of this. Instead, it starts the work, persists the job ID in state, and hibernates. When the result arrives—via a callback, a poll, or a workflow completion—the agent wakes, correlates the result, and moves on.

## Durable Objects and Hibernation

Durable Objects invert this model. An agent exists as an addressable entity with persistent state, but consumes zero compute when hibernated. When something happens—an HTTP request, a WebSocket message, a scheduled alarm, an inbound email—the platform wakes the agent, loads its state from SQLite, and hands it the event. The agent does its work, then goes back to sleep.

## Using Scheduled Alarms for Periodic Checks

For the 1-hour pattern you asked about, Durable Object alarm allows a Durable Object instance to be awakened at a fine-grained time in the future with an at-least-once execution model, with automatic retries built in. This enables you to schedule periodic wake-ups (e.g., every hour) to check status or perform work.

## Recent 2025-2026 Updates

Cloudflare Workflows, a durable execution engine for multi-step applications, now supports higher concurrency and creation rate limits through a rearchitectured control plane, helping scale to meet the use cases for durable background agents. Additionally, as agents become persistent and autonomous infrastructure, operating on behalf of users for hours or days, they need a durable, asynchronous execution engine for the work they are doing. Workflows provides exactly that: every step is independently retryable, the workflow can pause for human-in-the-loop approval, and each instance survives failures without losing progress.

CF Workers: Sustained 1-Hour Execution — Documented Patterns
The Core Problem
CF Workers are fire-and-die by design. A standard fetch() handler has a 30-second wall-time hard limit. ctx.waitUntil() does NOT extend this — it only allows cleanup after response transmission. Self-invoking via fetch() within the same worker does not reset the clock. This cannot be worked around within the standard Workers model.

There are four legitimate patterns. Here they are ranked by fitness for a 1-hour continuous queue processor.

Pattern 1: Cloudflare Workflows (BEST FIT for 1-hour queue processing)
Source: Cloudflare Workflows GA announcement | Workflows limits

How it works: Step-based durable execution engine built on Workers. Each step.do() call is independently retriable with state automatically persisted between steps. CPU is billed only for active execution; wall time between steps costs nothing.

Hard limits (Paid plan):

Max steps per workflow: 10,000 (configurable to 25,000)
Max sleep per step.sleep: 365 days
Sleep steps do NOT count toward the 10,000-step limit
CPU per step: 30 seconds default, configurable to 5 minutes
Wall time per step: unlimited
Overall workflow duration: theoretically unlimited across steps
Concurrent running instances: 50,000 (Paid); waiting/sleeping instances are free and excluded from this count
Max persisted state: 1 GB (Paid)
Pattern for 1-hour continuous queue:


export class QueueWorkflow extends WorkflowEntrypoint {
  async run(event, step) {
    while (true) {
      const batch = await step.do('fetch-batch', async () => {
        return await fetchNextQueueBatch(); // 30s CPU budget per step
      });
      if (batch.length === 0) {
        await step.sleep('idle-wait', '30 seconds');
        continue;
      }
      for (const item of batch) {
        await step.do(`process-${item.id}`, async () => {
          return await processItem(item);
        });
      }
    }
  }
}
Each step.do gets a fresh 30-second CPU budget and is independently retriable. The workflow persists across reboots, evictions, and deploys.

Verdict: Correct architecture for a 1-hour queue processor. You are not running one continuous 1-hour invocation — you are running a durable state machine that processes chunks indefinitely.

Pattern 2: Durable Objects + Alarms (GOOD — stateful, but more manual)
Source: DO Alarms docs | DO limits

How it works: A Durable Object sets a recurring alarm against itself. Each alarm invocation gets 15 minutes of wall time. The alarm reschedules itself before completing, creating a self-sustaining heartbeat.

Hard limits:

CPU per invocation: 30 seconds default, 5 minutes configurable
Wall time per alarm invocation: 15 minutes hard cap
Retry on failure: at-least-once, exponential backoff, up to 6 retries
Alarm schedule precision: minimum 1 second granularity
Pattern:


class QueueProcessor {
  async alarm() {
    // Each alarm gets 15 min wall time
    const batch = await this.fetchBatch();
    await this.processBatch(batch);
    // Reschedule itself to keep running
    await this.state.storage.setAlarm(Date.now() + 100); // 100ms gap
  }
}
Gap: 15-minute alarm cap means you cannot run one continuous invocation for an hour. You chain alarm → alarm → alarm. State must be persisted to DO SQLite between invocations. Gaps between alarms are possible (Cloudflare fires alarms "within a minute of the scheduled time" not exactly). For queue processing this is fine — items sit in queue until next alarm fires.

Verdict: Works for 1-hour operation via chained 15-minute invocations. More complex than Workflows — you own all state management. Better if you need tight stateful control (e.g., in-memory position tracking that you SQLite-persist yourself).

Pattern 3: Cloudflare Queues + Consumer Worker (GOOD — for pure throughput)
Source: How Queues works | DEV.to long jobs post

How it works: The queue consumer handler (queue()) has no CPU time limit — only a wall-time limit measured in minutes (not seconds). Cloudflare auto-scales concurrent consumers to drain the queue. Messages not acknowledged get redelivered.

Hard limits (from official docs and dev.to article):

CPU time: unlimited in queue consumer
Wall time: minutes (exact ceiling not documented; community reports 15 min per batch)
Max message size: 128 KB
Max batch size: 100 messages
Consumer concurrency: auto-scaled by CF based on queue depth and failure rate
At-least-once delivery; explicit ack/nack per message

export default {

Key distinction from Workflows: Queues are pull-based with CF-controlled delivery. You don't control the "loop" — CF does. If you need to sustain processing for 1 hour, you need items in the queue for 1 hour. The consumer runs continuously as long as items exist.

Verdict: Best for high-throughput processing where tasks are discrete and queue-resident. Not suitable if you need a single "session" that tracks shared state across 1 hour — each batch invocation is stateless.

Source: CF Agents long-running docs

Hard limits:

Wall time: unlimited while connection is open
Connection must remain open — if client disconnects, eviction can occur

Recommended Composite Formula (synthesized from HAL + TheAgentCompany)

Score(W) = (α × TasksCompleted/TasksAvailable)
         + (β × PartialCheckpointSum/MaxCheckpoints)
         + (γ × UniqueItemsFound/TotalItems)
         + (δ × ThreadsDiscovered/TotalThreads)
         − (ε × ErrorRate)
         − (ζ × CostSpent/CostBudget)
Where α + β + γ + δ = 1.0 and ε, ζ are penalty coefficients.

PCC-3 Research Report: Autonomous Agent Loop Patterns for Fixed Time Windows
WHAT WAS ASKED
Best practices for running an AI agent autonomously for 1 hour that: drains a backlog queue, logs discoveries, self-reports metrics, and competes against sibling agents.

PATTERN 1 — The Planner-Worker-Judge Triad (Most Proven)
Source: nibzard/awesome-agentic-patterns

The single most battle-tested pattern for long-running autonomous work. Three roles:

Planner — explores the queue/codebase, spawns sub-planners, creates tasks. Planning itself is parallelized and recursive.
Worker — operates in isolation, no cross-worker coordination. Executes only its assigned task.
Judge — evaluates whether objective is met or iteration should continue.
Key mechanic: "Fresh starts" at each cycle. Workers get a new context window per task to prevent drift and tunnel vision. This is the anti-pattern to long-context degradation.

Proven scale: Hundreds of concurrent workers running for weeks on large codebases.

Failure modes (documented):

Over-coordination: an "integrator" quality-control role created more bottlenecks than it solved — eliminated in production.
Early termination: models "tend to stop early and take shortcuts" — Judge layer is the mitigation.
Context drift: agents lose goal fidelity over long runs without fresh-start cycles.
PATTERN 2 — LangGraph StateGraph with Hard Budget Caps

export class RaceRunner {
  constructor(state, env) {
    this.state = state;
    this.env = env;
  }

  async fetch(request) {
    const url = new URL(request.url);
    if (url.pathname === '/start' && request.method === 'POST') {
      return this.handleStart(request);
    } else if (url.pathname === '/status') {
      return this.handleStatus();
    } else if (url.pathname === '/stop') {
      return this.handleStop();
    }
    return new Response('not found', { status: 404 });
  }

  async handleStart(request) {
    const body = await request.json().catch(() => ({}));
    const budget_ms = body.budget_ms || 3600000; // 1 hour default
    const now = Date.now();
    await this.state.storage.put('run_state', {
      start_time: now,
      budget_ms,
      batches_run: 0,
      actualizers_run: 0,
      discoveries_count: 0,
      errors_count: 0,
      death_runs: 0,
    });
    await this.state.storage.setAlarm(now + 1000); // first alarm in 1s
    return Response.json({ ok: true, started_at: now, budget_ms });
  }

  async alarm() {
    const state = await this.state.storage.get('run_state');
    if (!state) return;
    
    const elapsed = Date.now() - state.start_time;
    if (elapsed >= state.budget_ms) {
      // Race over - write final metrics
      await this.writeMetrics(state, true);
      return;
    }

    // Run one batch of work
    const batchResult = await this.runBatch(state);
    
    const updated = {
      ...state,
      batches_run: state.batches_run + 1,
      actualizers_run: state.actualizers_run + (batchResult.actualizers || 0),
      discoveries_count: state.discoveries_count + (batchResult.discoveries || 0),
      errors_count: state.errors_count + (batchResult.errors || 0),
      death_runs: state.death_runs + (batchResult.death_runs || 0),
    };
    
    await this.state.storage.put('run_state', updated);
    await this.writeMetrics(updated, false);
    
    // Schedule next alarm in 30s
    await this.state.storage.setAlarm(Date.now() + 30000);
  }

  async runBatch(state) {
    // PCC-Arch specialty: orchestrate PCC-2 and PCC-3 via service bindings
    let actualizers = 0;
    let discoveries = 0;
    let errors = 0;
    let death_runs = 0;

        const keys = await this.env.SOUL_KV.list({ prefix: 'pending:rrl:' });

          if (rrl_text) {
            const deathResult = await this.runDeathPipeline(run_number, rrl_text);
            if (deathResult.ok) {
              death_runs++;
              discoveries += deathResult.discoveries || 0;
              await this.env.SOUL_KV.delete(key.name);
            }
          }
        }
      }

        const r = await this.env.PCC2_SVC.fetch('https://pcc2/api/run-fleet').catch(() => null);

    }
    
    return { ok: true, ledger_id, soul_count, dna_count, soulkeys_hit, discoveries: soulkeys_hit + 1 };
  }

    const elapsed = Date.now() - state.start_time;
    const score = (state.batches_run * 10) + (state.actualizers_run * 5) + (state.discoveries_count * 20) + (state.death_runs * 50);
    const metrics = {
      agent_id: 'pcc-arch',

      elapsed_ms: elapsed,
      batches_run: state.batches_run,
      actualizers_run: state.actualizers_run,
      discoveries_count: state.discoveries_count,
      errors_count: state.errors_count,
      death_runs: state.death_runs,
      score,
      final,
    };
    if (this.env.SOUL_KV) {
      await this.env.SOUL_KV.put('race:pcc-arch:metrics', JSON.stringify(metrics));
    }
  }

  async handleStatus() {
    const state = await this.state.storage.get('run_state');
    if (!state) return Response.json({ ok: false, error: 'not started' });
    const elapsed = Date.now() - state.start_time;

  }

  async handleStop() {
    await this.state.storage.deleteAlarm();
    const state = await this.state.storage.get('run_state');
    await this.writeMetrics(state || {}, true);
    return Response.json({ ok: true, stopped: true });
  }
}
